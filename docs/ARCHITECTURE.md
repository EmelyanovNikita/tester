# Техническая документация: устройство тестера

Для тех, кто будет расширять проект. Пользовательская документация (запуск, конфиг, язык сценариев) — в [README](../README.md).

## 1. Назначение и принципы

Тестер играет роль SSW для MM: MM вызывает на нём `Connect` и присылает события, тестер вызывает на MM методы управления и (опционально) обменивается с ним RTP.

Принципы:
- **Команды не зашиты в код.** Методы, их аргументы, сообщения и enum загружаются из `.proto` MM во время запуска (`protoreflect`). Новый rpc в proto сразу доступен в сценариях.
- **Сообщения динамические** (`dynamic.Message`): нет сгенерированного кода и привязки к версии proto.
- **Один пакет — одна ответственность**, зависимости идут строго вниз (см. схему).
- **Всё, что можно, проверяется без MM**: RTP — локальными UDP-сокетами, парсер — строками, нагрузка — подставной функцией.

## 2. Структура репозитория

```
cmd/tester/
  main.go        флаги, конфиг, сборка частей, режимы запуска (одиночный/нагрузочный)
  scenarios.go   выбор и загрузка файлов сценариев, итог по нескольким сценариям
  server.go      gRPC-сервер тестера (сюда ходит MM): Connect → mmlink, остальное → events
internal/
  protoloader/   разбор .proto → методы, enum (MethodInfo, ProtoData)
  mmlink/        соединение с MM: Connect от MM, Dial, CredentialsSend, общий Link
  events/        буфер событий от MM + ожидание с условиями (Bus)
  scenario/      парсер языка, исполнитель, переменные, выражения, команды (wait_event, rtp_*)
  sdp/           разбор и сборка SDP (только то, что нужно RTP)
  rtp/           RTP-движок: кодеки, сеансы, DTMF, WAV, статистика
  load/          нагрузочный режим: ровный темп стартов, потолок, сводка
scripts/         примеры и боевые сценарии (simple, many_steps, mm_check)
config/          примеры конфига
docs/            документация
```

### Зависимости пакетов

```
cmd/tester ──► scenario ──► rtp ──► sdp
    │             └────────► protoloader
    ├──► mmlink
    ├──► events      (scenario знает только интерфейс EventSource; *events.Bus ему передаёт main)
    ├──► load ──► rtp   (load использует rtp.Stats для сводки, про сценарии не знает)
    └──► protoloader
```

`load` намеренно не знает ни про сценарии, ни про gRPC: ему передаётся функция `run(instance) CallResult`. `scenario` не знает про флаги и конфиг: всё нужное передаётся через `NewExecutor`, `SetConnector`, `SetRTP`, `SetEvents`, `SetInstance`, `SetQuiet`.

## 3. Поток данных

### Запуск (`cmd/tester/main.go`)

1. `pflag.Parse`, `loadConfig`.
2. `protoloader.LoadProto` → `ProtoData{Methods, Enums}`.
3. Поиск сценариев (`chooseScenarios` → `scenarios.go`), разбор **всех** через `scenario.NewParser(methods).Parse` — ошибки собираются и показываются разом.
4. `mmlink.New(establish)` — `Link`, `events.NewBus()`, `rtpFactory()` (`rtp.Factory` с диапазоном портов).
5. В горутине стартует `sswServer.serve` — gRPC-сервер со всеми сервисами из proto.
6. Режим: нагрузочный (`opts.Enabled()`) → `runLoadMode`; иначе по очереди `runScenario` для каждого файла.
7. Итог, `finish(code)`.

### Входящие вызовы (MM → тестер)

`server.go` регистрирует **все** методы всех сервисов из proto (динамический `grpc.ServiceDesc`). Обработчик декодирует запрос в `dynamic.Message` и:
- `Connect` → `mmlink.Link.OnConnect(params)` (запоминает session_id и адрес MM; повторные игнорируются), в ответ — успешный;
- всё остальное → `events.Bus.Publish(methodName, jsonСНулевымиПолями)` и пустой успешный ответ.

### Исходящие вызовы (тестер → MM)

`scenario.Executor.runCommand` для метода из proto: собирает `dynamic.Message` по аргументам (позиционные → поля запроса по порядку объявления, `convertStringToType` приводит строку к типу поля, включая enum, `repeated`, вложенные сообщения из JSON), делает `conn.Invoke` (таймаут 5 с), кладёт ответ в переменную как JSON с `EmitDefaults`, проверяет `reply_code`.

### Подключение к MM (`mmlink`)

- `Link` хранит параметры первого `Connect` и умеет `Ensure(ctx)`: ждёт `Connect`, вызывает `EstablishFunc` один раз, потом отдаёт кэшированный `Session` (соединение + session_id). Безопасен для параллельных вызовов — все клиенты нагрузки делят одно соединение.
- `connect.go`: `Dial` (повторы раз в секунду), `Authenticate` (`CredentialsSend`), `NewEstablisher` склеивает их. Если протокол подключения изменится — правится только этот файл.

## 4. Пакет scenario

### Парсер (`scenario.go`)

Построчный, без отдельного лексера. `Parse` → `parseBlock` рекурсивно разбирает блоки (`for`, `if/else`), каждая простая строка идёт в `parseLine`, который по порядку проверяет формы:

1. `sleep(...)`, `pause(...)`, `log(...)`, `fail(...)` (`logLikeRe`), `connect()`;
2. `wait_event(...)` и RTP-команды (`rtpKeyword`);
3. присваивание (`findAssignment`): справа простое значение, вызов метода, `wait_event` или `rtp_*`;
4. вызов метода MM (`parseCommand`);
5. иначе строка **игнорируется** (известная слабость — см. §9).

Результат — дерево `Command` (поля `IsFor`, `IsIf`, `IsSleep`, `IsRTP`, … + `Body`/`ElseBody`). Имя метода проверяется по `methods`, поэтому опечатки ловятся при разборе.

### Исполнитель (`executor.go`, `flow.go`)

`Executor` — один «клиент» сценария. Хранит: gRPC-соединение, переменные (`VarStorage`), `ExprParser`, RTP-сеансы (`rtpSessions`), источник событий (`EventSource`), номер клиента (`instance`), префикс лога и «тихий» режим. `Execute(scenario)` (flow.go) обходит дерево через `runBlock`; `runCommand` — диспетчер по флагам команды (см. цепочку `if cmd.IsSleep … cmd.IsRTP …` в `executor.go`). Нумерация команд для логов (`2.1`) — в `flow.go`.

Ошибка команды останавливает сценарий (если не `continueOnError`); счётчик ошибок определяет код возврата.

### Выражения и переменные (`expr.go`, `vars.go`)

Все значения — строки. `ExprParser.ResolveValue` — единственное место, где токен превращается в значение: строка → JSON → bool/null → число → `var.path` → enum → переменная. Если добавляете новую форму значения, добавляйте её сюда и покрывайте таблицей тестов. `VarStorage.SetField` пишет в поле JSON-объекта (`a.b.c = v`).

Сравнения в `if`/`wait_event` (`parseCondition` разбирает запись, `compareValues` в `flow.go` сравнивает): числа — точно (`math/big`), enum приводятся к числу (`enumToNumber`), иначе строки.

### События (`events.go`, `internal/events/bus.go`)

`Bus` — буфер последних 10 000 событий (`name`, JSON, флаг `consumed`). `Publish` — из gRPC-сервера, `Wait(name, match, timeout)` — из исполнителя: ищет самое раннее неиспользованное подходящее событие, иначе ждёт новых (канал `changed` закрывается при каждой публикации) до таймаута. При таймауте `TimeoutError` содержит диагностику. `Executor` обращается к шине через интерфейс `EventSource` (`SetEvents`).

`Bus.Reset()` вызывает `main.go` перед каждым сценарием: события предыдущего сценария не видны следующему, а пришедшие между `Reset` и `wait_event` не теряются. В нагрузочном режиме шина общая.

### RTP-команды (`rtpcmd.go`)

Спецификация команд — таблица `rtpSpecs` (мин/макс позиционных аргументов, допустимые именованные). Парсер проверяет её при разборе; исполнитель (`runRTP`) делегирует `rtpOpen/rtpStart/rtpDTMF/rtpFinish`. Сеансы хранятся в `executor.rtpSessions` по `id`; `closeRTP` (defer в `Execute`) в конце сценария останавливает забытые и пишет предупреждение. Итоговые счётчики остановленных сеансов копятся в `rtpFinal` (для сводки нагрузки) — см. `instance.go`.

## 5. Пакет rtp

| Файл | Содержимое |
|---|---|
| `codec.go` | `Codec` (PCMU, PCMA, G722, L16, telephone-event), `ParseCodec`, `MatchSDP`, размеры кадра, `Encoder`/`Decoder` |
| `g711.go`, `g722.go` | кодеки на чистом Go; G.722 побитово совпадает с эталоном `ffmpeg` (`testdata/ref*.g722`) |
| `toneloop.go` | тон кодируется **один раз** в циклический буфер кадров (`frameLoop`), общий для всех сеансов (кэш по кодеку/ptime/частоте) — отправка = копирование байт |
| `dtmf.go` | события telephone-event (RFC 4733): кодирование, повторы конца события |
| `packet.go` | заголовок RTP: сборка и разбор |
| `wav.go` | запись принятого звука в WAV |
| `session.go` | `Factory` (выдача портов), `Session` (приём, отправка, статистика) |

### Factory

Выдаёт чётные порты из `[portMin, portMax]`, начиная со случайного (`RandomizeStart`) — чтобы запуск не попадал на порты предыдущего (MM после `ChannelRemove` может ещё слать RTP). Порты — общий ресурс для всех клиентов нагрузки (под мьютексом `Factory`).

### Session: жизненный цикл

`Factory.Open` → занимает UDP-порт, строит offer (`sdp.Offer`) → `Start(StartOptions)`: разбирает SDP-ответ (`chooseCodec`, `chooseEventPT`), определяет адрес назначения и ptime и запускает две горутины: `receiveLoop` (`handlePacket` → `trackSequence`, `updateJitter`, запись, DTMF) и `sendLoop` (тикер по ptime, кадры из `frameLoop`, вставка DTMF) → `Stop()` закрывает сокет и возвращает `Stats`.

### Статистика

- Потери и порядок — RFC 3550 App. A.1 (`trackSequence`), джиттер — RFC 3550 (`updateJitter`).
- При смене SSRC приёмник переключается на новый источник и **сбрасывает** джиттер; поэтому два потока на одном порту дают `jitter_ms ≈ 0` и `sources > 1`. Ограничение `maxTrackedSources = 64`.
- Чужие payload type считаются в `other_payload_packets/Types`.

## 6. Нагрузочный режим (`internal/load`, `cmd/tester`)

`load.Run(opts, stop, run)` запускает вызовы функции `run(instance)` по фиксированному расписанию: момент следующего старта `next` растёт на `1/Rate` независимо от того, когда звонки завершаются, поэтому старты равномерны. `Limit` (канал-семафор) только потолок одновременных звонков: если старт задержался из-за потолка более чем на интервал, расписание сдвигается на текущий момент, а не нагоняется (иначе после упора случился бы всплеск). `Calls == 0` — без предела; закрытие `stop` (Ctrl+C в `cmd/tester`) прекращает запуск и ждёт идущих. Результаты — `[]CallResult` (ошибка, длительность, RTP-статистика), раз в 5 секунд печатается ход. `Summary` строит текстовую сводку и код возврата. `runSafely` превращает панику клиента в ошибку этого клиента.

В `main.go` `runScenarioLoad` на каждый клиент создаёт **свой** `Executor` (`newExecutor`), задаёт `SetInstance(n, true)`, `SetQuiet(!verbose)`, при отсутствии `connect()` в сценарии вызывает `EnsureConnected()`. Общие: `Link` (соединение с MM), `events.Bus`, `rtp.Factory`, разобранное дерево сценария (только для чтения).

## 7. Как расширять

### Добавить новую команду MM

Ничего не делать: добавьте rpc в proto — он появится в сценариях автоматически.

### Добавить новую встроенную команду (как `sleep`)

1. `scenario.go`: поле в `Command` (`IsXxx`), regexp/распознавание в `parseLine` (до разбора вызова метода MM), тест на разбор в `scenario_test.go` (включая ошибки).
2. `executor.go`: ветка в `runCommand`, реализация в `flow.go` (или новом файле).
3. Если команда должна быть видна в нумерации/блоках — проверить `flow.go`.
4. Документация: раздел «Работа со сценариями» в README.

### Добавить RTP-команду или параметр

Запись в `rtpSpecs` (имя, число аргументов, допустимые именованные), обработка в `runRTP`/`rtpOptions`, при необходимости поле в `rtp.OpenOptions`/`StartOptions`. Тест в `rtp_test.go` и `TestParseRTPErrors`.

### Добавить кодек

1. `codec.go`: константа `Codec` (имя, payload type по умолчанию, clock rate, kind), ветки в `ParseCodec`, `MatchSDP`, `FrameSamples`/`PayloadBytes`, `NewEncoder`/`NewDecoder`.
2. Реализация `Encoder`/`Decoder` (отдельный файл, как `g722.go`).
3. Эталонный тест: сравнение с независимой реализацией (как G.722 с `ffmpeg`), круговой тест encode→decode.
4. `toneloop.go` менять не нужно, если кодек реализует интерфейсы.
5. Сценарий проверки в `scripts/mm_check/` (папка запускается целиком: `-s scripts/mm_check`).

### Добавить поле в счётчики RTP

`rtp.Stats` (+ `snapshot`), при необходимости агрегация в `load.rtpSummary`, описание в README, раздел «Счётчики RTP».

### Новый вид события / ожидание

События универсальны: любой метод, вызванный MM на тестере, уже попадает в `Bus`. Для нового вида ожидания расширяйте `executor.runWaitEvent`/`events.Bus.Wait`.

### Новый транспорт/тип подключения

Только `mmlink/connect.go`.

## 8. Тестирование

- `go test ./...` — не требует MM и сети (кроме loopback UDP).
- `scenario`: парсер (таблицы корректных и ошибочных сценариев), выражения, `if`/`for`/`fail`, запись в поле, параллельный запуск (`parallel_test.go`, запуск с `-race`).
- `rtp`: кодеки (границы, круговые тесты, G.722 против эталонных файлов), пакеты, DTMF, трекинг последовательности, запись WAV, сеансы через loopback.
- `load`: `Run`/`Summary` на подставной функции (равномерность стартов, потолок, остановка, паника, перцентили).
- `cmd/tester`: разбор опций нагрузки и секции `load` конфига.
- Что **не** покрыто автотестами: реальный gRPC (`executor.go` вызов `Invoke`, `server.go`) и взаимодействие с настоящим MM — это проверяется скриптами `scripts/mm_check` и `scripts/many_steps/call_rtp.txt`.
- Правило: сценарии в `scripts/` должны быть корректны относительно текущего proto (имена методов, число аргументов, ключи JSON, имена enum).

## 9. Известные ограничения и идеи развития

- Парсер молча пропускает нераспознанные строки — стоит сделать это ошибкой (отдельный флаг строгого режима).
- Литералы `{...}` и `[...]` без подстановки переменных. Возможное решение — шаблонизация `${var}`.
- Нет `&&`/`||`/`else if`, арифметики, строковых функций.
- Один MM на запуск; несколько тестеров/управляющих серверов — отложено.
- Нет отправки готовых RTP-кадров из файла (pcap или собственный формат — не решено), нет видео и кодеков за пределами PCMU/PCMA/G.722/L16.
- Не выяснено: при двух запусках подряд на реальном MM принятых пакетов бывает ровно вдвое больше (см. `sources` в статистике; гипотезы — остаточный поток на переиспользованном порту либо поток на удвоенной скорости).
- DTMF, принятый MM, виден только в логе MM; можно ждать событие `DTMFDetected` через `wait_event` в `scripts/mm_check/dtmf.txt`.
