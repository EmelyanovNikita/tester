# Работа с тестером: руководство пользователя

Тестер эмулирует SSW (управляющий сервер) для media-manager (MM): принимает от MM `Connect`, подключается к нему, выполняет сценарии (вызовы gRPC-методов MM), принимает события от MM и умеет слать и принимать настоящий RTP. Язык сценариев описан в [SCRIPTING.md](SCRIPTING.md), устройство программы — в [ARCHITECTURE.md](ARCHITECTURE.md).

## 1. Сборка и запуск

```
go build -o tester ./cmd/tester
./tester -p config/config.json -s scripts/simple/channel_add.txt
```

Требуется Go 1.22+. Файлы `.proto` MM должны лежать на диске: путь к ним указывается в конфиге.

### Как проходит запуск

1. Читается конфиг, загружаются proto-файлы (из них берутся методы, сообщения и enum — отдельного списка команд в тестере нет).
2. Разбираются **все** сценарии. Ошибка синтаксиса в любом из них останавливает тестер до начала работы.
3. Поднимается gRPC-сервер тестера (`local_server`), на котором MM вызывает `Connect`.
4. По `connect()` в сценарии (или автоматически перед сценарием) тестер дожидается `Connect` от MM, подключается к MM и аутентифицируется (`CredentialsSend`).
5. Выполняются сценарии, в конце печатается итог. Код возврата: `0` — всё успешно, `1` — были ошибки.

## Базовые команды

Три готовых примера, с которых удобно начать. Запускать можно из любой папки; путь к конфигу (по умолчанию `config/config.json`) отсчитывается от корня репозитория. Скрипты используют собранный `./tester`, а если его нет — `go run`.

| Что | Команда | Что делает |
|---|---|---|
| Один звонок | `./scripts/run_call.sh config/config.json` | полный звонок с настоящим RTP: два плеча, тон, DTMF, проверки; записывает `call_A_1.wav` и `call_B_2.wav` |
| Все простые сценарии | `./scripts/run_simple.sh config/config.json` | по очереди все сценарии из `scripts/simple` (каналы, аудио, DTMF, детектор громкости, RTP) с `--continue-on-error`; в конце итог по каждому сценарию |
| Нагрузочный тест | `./scripts/many_steps/load_100_calls.sh config/config.json` | 100 одновременных звонков из `call_rtp.txt`, по 20 стартов в секунду, в конце сводка |

Дополнительные флаги тестера дописываются в конец: `./scripts/many_steps/load_100_calls.sh config/config.json --parallel 20 --verbose`. Другое число звонков — флагами `--parallel/--calls/--rate` (см. раздел 6). То же без скриптов:

```
./tester -p config/config.json -s scripts/many_steps/call_rtp.txt
./tester -p config/config.json --continue-on-error -s scripts/simple
./tester -p config/config.json -s scripts/many_steps/call_rtp.txt --parallel 100 --rate 20
```

Проверка кодеков и DTMF на MM — отдельно: `./scripts/mm_check/run.sh config/config.json`.

## 2. Флаги

| Флаг | Описание |
|---|---|
| `-p`, `--path` | путь к конфигу (обязателен) |
| `-s`, `--scenario` | сценарии: файлы или папки. Можно списком через запятую, повторением флага или шаблоном shell (`-s scripts/simple/*`); всё, что идёт после `-s` в командной строке, считается сценариями |
| `--continue-on-error` | не останавливать сценарий на первой ошибке команды; в конце код возврата 1, если ошибки были |
| `--keep-alive` | не завершаться после сценария (чтобы MM мог продолжать присылать события) |
| `--parallel N` | нагрузочный режим: N клиентов одновременно |
| `--calls M` | всего запусков сценария (по умолчанию = `--parallel`) |
| `--rate R` | не больше R запусков в секунду (0 — без ограничения) |
| `--verbose` | в нагрузочном режиме выводить подробный лог каждого клиента |

Откуда берутся сценарии (по убыванию приоритета): флаг `-s` → поле `scenarios` в конфиге → файл `scenario.txt` в текущей папке. Из папки берутся `*.txt` без вложенных папок, по алфавиту.

## 3. Конфиг

```json
{
  "proto_root": "/path/to/ecss-media-manager-api-proto",
  "proto_files": [
    "mm/client_api/v1/mm_client_api.proto",
    "mm/objects/v1/mm_objects.proto",
    "mm/server_api/v1/mm_server_api.proto"
  ],
  "local_server": { "address": "0.0.0.0", "port": 7000 },

  "scenarios": ["scripts/simple", "scripts/many_steps/call.txt"],
  "start_delay_sec": 3,
  "load": { "parallel": 100, "calls": 100, "rate": 20 },
  "rtp": { "ip": "10.30.100.108", "port_min": 20000, "port_max": 30000 }
}
```

| Поле | Обязательно | Описание |
|---|---|---|
| `proto_root`, `proto_files` | да | где лежат proto MM; из них строятся все команды сценариев |
| `local_server.address/port` | да | где тестер слушает вызовы MM (`Connect` и события). MM должен быть настроен на этот адрес |
| `scenarios` | нет | сценарии по умолчанию, если нет `-s` |
| `start_delay_sec` | нет (3) | пауза после подключения к MM перед сценарием **без** своего `connect()`: MM нужно время, чтобы подключить свои серверы. `0` — без паузы |
| `load` | нет | значения `--parallel/--calls/--rate` по умолчанию; явно указанный флаг главнее |
| `rtp.ip` | нет (`127.0.0.1`) | адрес, который тестер пишет в SDP и на котором слушает RTP. **Должен быть доступен для MM** (не `127.0.0.1`, если MM на другой машине) |
| `rtp.port_min/port_max` | нет (20000–30000) | диапазон UDP-портов для RTP. Порты чётные; на звонок нужно по порту на каждое плечо |

## 4. Подключение к MM

Подробности синтаксиса — в SCRIPTING.md, раздел `connect()`. Коротко:

- В сценарии есть `connect()` — тестер ждёт `Connect` от MM в этом месте, пауза после него — обычный `sleep(...)`.
- `connect()` нет — тестер подключается сам перед сценарием и ждёт `start_delay_sec`.
- Соединение одно на весь запуск и общее для всех сценариев и клиентов нагрузки.
- Если MM не вызвал `Connect`, тестер ждёт; не забудьте перезапустить/переподключить MM к адресу `local_server`.

## 5. Несколько сценариев

```
./tester -p config/config.json -s scripts/simple
```

Сценарии идут по очереди. Ошибка одного не мешает следующим (кроме случая, когда нет соединения с MM совсем: остальные помечаются пропущенными). У каждого сценария свои переменные. В конце — итог:

```
Итог: сценариев 3, успешно 2, с ошибками 1
  OK       scripts/simple/channel_add.txt (0.4 с)
  ОШИБКА   scripts/simple/channel_audit.txt (0.2 с): сценарий остановлен на команде 2: ...
```

## 6. Типовые задачи

### Один звонок с настоящим RTP

```
./tester -p config/config.json -s scripts/many_steps/call_rtp.txt
```

Сценарий создаёт два плеча, шлёт тон и DTMF, проверяет счётчики пакетов (`fail` при проблемах) и записывает принятый звук в WAV (`call_A_*.wav`, `call_B_*.wav`) — его можно послушать.

### Проверка кодеков и DTMF на реальном MM

```
./scripts/mm_check/run.sh config/config.json
```

По сценарию на кодек (PCMU, PCMA, G.722, L16/16000), на ptime 10/30 мс и на DTMF. В конце — ОК/ПРОВАЛ по каждому, код возврата 0 только если всё прошло. Если не проходит один кодек (у нас `L16`), смотрите, включён ли он на MM: без него MM отвечает `RC_INTERNAL_ERROR` на `ChannelAdd`.

### Нагрузочный тест

```
./tester -p config/config.json -s scripts/many_steps/call_rtp.txt --parallel 100 --rate 20
./scripts/many_steps/load_100_calls.sh config/config.json      # то же, готовый запуск
```

#### Как работают `--parallel`, `--calls`, `--rate`

Каждый «звонок» — один полный прогон сценария одним клиентом. Клиенты нумеруются от 1 до `calls` (это `INSTANCE`). Три флага отвечают на три разных вопроса:

| Флаг | Вопрос | По умолчанию |
|---|---|---|
| `--calls M` | сколько всего звонков сделать за тест | равно `--parallel` |
| `--parallel N` | сколько звонков могут идти **одновременно** | 1 |
| `--rate R` | сколько новых звонков можно **начинать** в секунду | 0 (без ограничения) |

Тестер запускает звонки по очереди с 1-го по M-й. Перед каждым стартом он ждёт двух условий:
1. идёт меньше N звонков (иначе ждёт, пока какой-то завершится) — это `--parallel`;
2. с предыдущего старта прошло `1/R` секунды — это `--rate`.

Примеры (звонок из `call_rtp.txt` идёт около 12 с):

| Запуск | Что происходит |
|---|---|
| `--parallel 100` | 100 звонков, все стартуют почти одновременно (пачкой) |
| `--parallel 100 --rate 20` | те же 100 звонков, но по 20 стартов в секунду: набор поднимается за 5 с, около 100 звонков идут одновременно (это `load_100_calls.sh`) |
| `--parallel 10 --calls 100` | всего 100 звонков, постоянно идут 10: как только один завершился, стартует следующий; весь тест около двух минут |
| `--parallel 50 --calls 1000 --rate 10` | 10 стартов/с × 12 с дали бы ~120 одновременных, но потолок 50, поэтому реальный темп снизится до ~4 звонков/с (50 / 12 с) |

Что часто путают:
- `--parallel` ограничивает звонки, идущие **сейчас**, а не всего; общее число задаёт `--calls`.
- `--rate` ограничивает только скорость **запуска**. Сколько звонков идёт одновременно, определяют длительность звонка и `--parallel`; ориентировочно `rate × длительность`, но не больше `parallel`.
- Если `--calls` меньше `--parallel`, лишние места просто не используются.

Какую нагрузку задаёт какая комбинация:
- поднять N звонков и подержать: `--parallel N`, в сценарии `sleep` на нужную длительность, `--rate` для плавного набора;
- постоянно ровно N звонков, всего M: `--parallel N --calls M` (M больше N);
- заданная интенсивность, например 5 звонков в секунду: `--rate 5`, большой `--parallel` (чтобы он не ограничивал), нужный `--calls`.

Те же значения можно задать в конфиге (`"load": {"parallel": 100, "calls": 100, "rate": 20}`); явный флаг главнее.

#### Остальное про нагрузочный режим

- У каждого клиента свои переменные, RTP-порты и RTP-сеансы; номер клиента — переменная `INSTANCE`. Строки лога начинаются с `[#N]`.
- Ход печатается раз в 5 секунд. В конце — сводка:
  - клиентов успешно/с ошибкой и процент успеха;
  - длительность звонков: мин / средняя / 95-й процентиль / макс;
  - RTP по всем потокам: отправлено / принято / потеряно, средний и максимальный джиттер;
  - потоки без входящего звука, потоки с несколькими SSRC, DTMF, чужие payload type;
  - ошибки, сгруппированные по тексту, с числом клиентов.
- Код возврата 1, если хоть один клиент провален.
- Диапазон портов должен вмещать все одновременные звонки (2 порта на звонок × `parallel`): для 100 звонков — 200 портов, по умолчанию их 5000.
- Чтобы не плодить сотни WAV-файлов, пишите звук только у одного клиента: `if INSTANCE == 1 { ... }`.
- Общие для клиентов события: в `wait_event` обязательно фильтруйте по идентификаторам своего канала.

## 7. Как читать лог

```
2026/10/08 12:00:01 [1] Команда: ChannelAdd
2026/10/08 12:00:01 Запрос для ChannelAdd: {...}
2026/10/08 12:00:01 Ответ для ChannelAdd: {...}
```

- `[N]` — номер команды в сценарии; внутри `for`/`if` — `2.1`, `2.2` (номер блока.номер команды).
- «Получен запрос: …» — событие от MM (оно попадает в буфер для `wait_event`).
- `log: …` — вывод команды `log(...)`.
- Итог RTP при `rtp_stop`: кодек, отправлено/принято/потеряно, джиттер и т. п.

## 8. Как понимать счётчики RTP

| Поле | Смысл |
|---|---|
| `sentPackets` / `receivedPackets` | пакеты, отправленные нами / принятые от MM (только согласованный audio payload) |
| `lostPackets`, `lossPercent` | потери по разрывам в sequence number (RFC 3550) |
| `outOfOrderPackets`, `duplicatePackets` | переупорядочение и дубли |
| `jitterMs` | межпакетный джиттер по RFC 3550 |
| `dtmfSent`, `dtmfReceived`, `dtmfPackets` | цифры и пакеты telephone-event |
| `otherPayloadPackets`, `otherPayloadTypes` | пакеты с чужим payload type (например, MM шлёт 101, а договорились о 96) |
| `sources` | сколько разных SSRC принято. Больше 1 — в поток подмешан чужой источник (например, остатки предыдущего звонка на том же порту) |
| `badPackets` | не RTP |

Если `receivedPackets` примерно вдвое больше ожидаемого, а `jitterMs` около 0 — посмотрите `sources`: скорее всего, два потока на один порт. Подробнее — раздел 9.

## 9. Диагностика

| Симптом | Что проверить |
|---|---|
| Тестер «висит» на `connect()` | MM не вызвал `Connect`: адрес/порт `local_server` в настройках MM, доступность порта |
| `нет соединения с MM` при вызове метода | в сценарии `connect()` есть, но стоит ниже первого вызова метода — переместите его в начало |
| `метод X не найден` | опечатка или proto не той версии; список методов берётся из `proto_files` |
| `reply_code ... не RC_SUCCESS`, сценарий остановлен | это ожидаемое поведение; запустите с `--continue-on-error`, если хотите проверять статус в `if` |
| ChannelAdd → `RC_INTERNAL_ERROR` на конкретном кодеке | кодек не включён на MM (так у `L16`) |
| `receivedPackets = 0` | MM шлёт на другой адрес: проверьте `rtp.ip` (виден ли он MM), `c=` в SDP-ответе, firewall |
| Принято вдвое больше пакетов, `sources` > 1 | на порт приходит ещё и поток от прошлого запуска. Порты выдаются со случайного места, но если ситуация осталась — запустите ещё раз с паузой или сузьте/сдвиньте диапазон |
| `L16` не проходит | см. выше; остальные кодеки проверяются независимо |
| `wait_event` по таймауту | в ошибке показаны пришедшие события с тем же именем, но не подошедшие под условия — сравните поле и значение |
| Команда «молча» ничего не делает | парсер игнорирует строки, которые не распознал (известная слабость); проверьте синтаксис по SCRIPTING.md |
