# Язык сценариев: справочник

Сценарий — текстовый файл (по соглашению `.txt`), команды выполняются сверху вниз. Все примеры ниже есть в `scripts/`. Запуск и конфиг — в [USAGE.md](USAGE.md).

## 1. Общие правила

- Одна команда — одна строка. Исключение — блоки `for` и `if` (`{ ... }`).
- Комментарии: строка, начинающаяся с `#` или `//`.
- Пустые строки игнорируются.
- **Опасность:** строка, которую парсер не распознал как команду, пропускается без ошибки. Опечатка в `sleep`/`log` может остаться незамеченной — проверяйте вывод сценария на первом запуске.
- Все сценарии разбираются до запуска; неизвестный метод MM, неверное число аргументов `rtp_*`, незакрытая скобка — ошибка при разборе с номером строки.

## 2. Значения и переменные

Любой аргумент и правая часть присваивания — «значение». Значения вычисляются в таком порядке:

| Запись | Что это |
|---|---|
| `"текст"` | строка; внутри работают `\r`, `\n`, `\t`; запятая и скобки внутри кавычек безопасны |
| `123`, `0.5`, `-4` | число |
| `true`, `false`, `null` | булево / null |
| `[ ... ]`, `{ ... }` | JSON-массив/объект «как есть» (см. ниже) |
| `var.field.sub` | поле объекта в переменной (JSON); числа остаются точными, в том числе 64-битные ID |
| `ИМЯ_ENUM` | значение enum по имени из proto, например `RC_SUCCESS`, `ACT_MODIFY` |
| `var` | значение переменной |
| `SESSION_ID`, `INSTANCE` | встроенные переменные (см. ниже) |

Неизвестное имя — ошибка «непонятное rvalue значение».

### Присваивание

```
sdp = "v=0\r\n..."          # строка
n = 5
chan = ChannelAdd(...)       # результат вызова метода MM → JSON ответа (с нулевыми полями)
```

Переменные — строки; объекты хранятся как JSON. Из ответа читаем `chan.channel_id`, `chan.reply_code` Имена полей **везде такие же, как в proto** (`channel_id`, `reply_code`): в переменных, в логе запросов и ответов, в условиях `wait_event`. Запись `chan.channelId` не работает; при опечатке ошибка перечисляет доступные поля.

### Запись в поле объекта

```
port_info = {"action": "ACT_MODIFY", "sdp_answer": "", "sdp_offer": ""}
port_info.sdp_answer = rtp_b.sdp        # переменная.поле = значение
port_info.inner.x = 5                   # вложенные поля
```

Справа — значение (строка, число, переменная, `var.поле`); результат команды в поле записать нельзя. Переменная должна существовать и быть объектом.

### Встроенные переменные

- `SESSION_ID` — идентификатор сессии, полученный от MM в `Connect`. Определена после `connect()`.
- `INSTANCE` — номер клиента в нагрузочном режиме (с 1; в обычном запуске всегда 1).

### Объекты и массивы в аргументах

```
audio_info = [{"type": 2, "url_file": "http://example.com/file.wav", "duration": 10}]
dtmf = {"type": 1, "pass_through_mode": false}
```

- Внутри `{...}` и `[...]` **подстановки переменных нет**: это JSON, который передаётся как есть (имена полей — ровно как в proto, например `on_ms`; неизвестное поле — ошибка). Чтобы вставить переменную, соберите объект по частям: `obj = {...}`, потом `obj.field = var`.
- Имена enum внутри JSON пишутся строкой: `"action": "ACT_MODIFY"`.
- Вложенные `oneof` задаются именем поля: `{"tone_info": {...}}` (см. `channel_audio_sequence_play.txt`).

## 3. Вызов метода MM

```
resp = ChannelAdd(SESSION_ID, 0, 0, true, sdp_offer, 0, "")
ChannelRemove(SESSION_ID, resp.channel_id)
```

- Имя метода — как в proto (`ChannelAdd`, `ChannelRemove`, `ChannelAudioFilePlay`, …). Любой rpc из загруженных proto доступен без изменений тестера.
- Аргументы идут **по порядку полей запроса в proto** (по номеру в объявлении сообщения). Для `ChannelAddRequest`: `session_id, context_id, channel_id, need_media, sdp_offer, media_profile_id, site`. Недостающие хвостовые аргументы остаются значениями по умолчанию; лишние — отбрасываются.
- `resp = ...` необязательно. Без него ответ только логируется.
- Если в ответе есть `reply_code` и он не `RC_SUCCESS` — команда считается ошибкой, сценарий останавливается (но ответ всё равно сохраняется в переменную). С `--continue-on-error` сценарий идёт дальше, код возврата в конце — 1.
- Таймаут вызова — 5 секунд.
- Вызов метода до `connect()` (если он есть в сценарии) — ошибка «нет соединения с MM».

## 4. Управление потоком выполнения

### for

```
for i in 1..100 {
    resp = ChannelAdd(SESSION_ID, 0, 0, true, sdp_offer, 0, "")
    resp = ChannelRemove(SESSION_ID, resp.channel_id)
}
```

Границы включительно: число или переменная (`1..n`). Если `a > b`, тело не выполняется. Переменная цикла доступна в теле и после цикла. Циклы вкладываются. В логе команды внутри цикла нумеруются `2.1`, `2.2`.

### if / else

```
if resp.reply_code == RC_SUCCESS {
    ...
} else {
    log("не удалось:", resp.reply_code)
}
```

- Одно сравнение: `==  !=  <  >  <=  >=`. Нет `&&`, `||`, `else if` (вкладывайте `if`).
- Оба значения числа → числовое точное сравнение (большие ID не теряют точность, `2 < 10`). Иначе `==`/`!=` сравнивают строки, а `<`, `>` и т. п. дают ошибку.
- Имя enum приводится к числу, `resp.reply_code == RC_SUCCESS` работает.
- Чтобы проверять `reply_code` в `if`, запускайте с `--continue-on-error` (иначе сценарий остановится раньше).

### Стиль скобок

`{` можно писать в конце строки или на следующей; `else` — после `}` или с новой строки; между ними допустимы пустые строки и комментарии. `}` — всегда на отдельной строке (или `} else {`).

### sleep

`sleep(2)`, `sleep(0.5)`, `sleep(delay)` — пауза в секундах.

### log и fail

```
log("канал:", resp.channel_id, "код:", resp.reply_code)
fail("мало пакетов:", st.received_packets)
```

- `log` печатает аргументы одной строкой через пробел (`log: ...`).
- `fail` печатает так же и завершает команду **ошибкой**: сценарий останавливается (с `--continue-on-error` идёт дальше, но завершится с кодом 1). В нагрузочном режиме клиент считается проваленным, текст попадает в сводку ошибок.
- Типичная проверка: `if st.received_packets < 20 { fail("мало пакетов:", st.received_packets) }`.

### connect()

```
connect()
sleep(3)
resp = ChannelAdd(SESSION_ID, ...)
```

Ждёт `Connect` от MM, подключается и аутентифицируется. Если соединение уже есть — пропускается, поэтому безопасно ставить в начало каждого сценария. Без `connect()` в сценарии тестер подключается сам перед запуском и ждёт `start_delay_sec`. С `connect()` пауза после него — обычный `sleep`.

## 5. wait_event — ожидание событий от MM

MM не только отвечает на запросы, но и вызывает методы на тестере (события: `AudioFilePlayed`, `AudioSequencePlayed`, `DTMFDetected`, `RtpIncoming` и др.). Чтобы не гадать `sleep`'ом:

```
play = ChannelAudioFilePlay(SESSION_ID, chan.channel_id, audio_info)
ev = wait_event(AudioFilePlayed, channel_id == chan.channel_id, player_id == play.player_id, 15)
log("проиграно, player_id:", ev.player_id)
```

- Синтаксис: `[переменная =] wait_event(ИмяСобытия, условие, ..., секунды)`. Имя — метод proto, который MM вызывает на тестере (можно в кавычках); опечатка ловится при разборе.
- Условие: `поле оператор значение`; слева поле события (имя как в proto и в логе, вложенные через точку), справа любое значение сценария. Операторы — как в `if`. Должны выполниться все условия.
- Последний аргумент без оператора — таймаут в секундах (число/переменная, дробный, `0` — только проверить уже пришедшие). По умолчанию 10 с.
- Событие, пришедшее **до** `wait_event`, не теряется (события копятся с начала сценария). События предыдущих сценариев не учитываются.
- Каждое событие забирается один раз: два `wait_event` подряд получат два разных события, по порядку прихода.
- По таймауту ошибка показывает, что пришло на самом деле (события с таким именем, не подошедшие под условия, и счётчики остальных), так видны опечатки в поле или значении.
- В нагрузочном режиме обязательно фильтруйте по своим идентификаторам (`channel_id == ...`): события общие для всех клиентов.

## 6. RTP-команды

Тестер может слать и принимать настоящий RTP на порты из SDP. Кодеки: PCMU, PCMA, G.722, L16 (8–48 кГц), DTMF — telephone-event (RFC 4733). Звук — синусоида заданной частоты.

```
rtp  = rtp_open()                                # занять порт; rtp.sdp — готовый SDP-offer
chan = ChannelAdd(SESSION_ID, 0, 0, true, rtp.sdp, 0, "")
rtp_start(rtp, chan.sdp_answer, tone = 440, record = "in_{id}.wav")
sleep(5)
st = rtp_stop(rtp)
log("принято:", st.received_packets, "потеряно:", st.lost_packets)
```

| Команда | Что делает |
|---|---|
| `r = rtp_open(...)` | занимает UDP-порт, в `r`: `id`, `ip`, `port`, `sdp` (offer) |
| `rtp_start(r, sdp_ответа, ...)` | берёт из ответа MM адрес, порт, кодек и `ptime`, запускает отправку и приём |
| `rtp_dtmf(r, "123#", ...)` | шлёт цифры в том же потоке, возвращается, когда переданы |
| `st = rtp_stats(r)` | текущие счётчики |
| `st = rtp_stop(r)` | останавливает поток, освобождает порт, итоговые счётчики |

**rtp_open** (все параметры необязательны, именованные `имя = значение`):

| Параметр | Описание |
|---|---|
| `ip` | адрес в SDP и для сокета |
| `port` | конкретный порт вместо свободного |
| `codecs` | `"PCMA"`, `"PCMA,PCMU"`, `"G722"`, `"L16/16000"`, `"PCMA,telephone-event"`; порядок = предпочтение; по умолчанию `PCMU,PCMA` |
| `dtmf_pt` | payload type telephone-event, 96–127 (по умолчанию 101) |
| `ptime` | мс (по умолчанию 20) |

Вместо параметров можно передать готовый SDP: `rtp_open(sdp_offer)` — берутся адрес и порт из него.

**rtp_start**: `tone` — частота, Гц, целое (440; `0` — тишина); `record` — WAV для принятого звука (`{id}` в имени заменяется номером сеанса; на месте потерянных пакетов тишина; 8 кГц, у G.722 и L16/16000 — 16 кГц; моно, 16 бит); `send = false` — только принимать; `host` — слать на этот адрес вместо адреса из SDP.

**rtp_dtmf**: `duration` — длительность цифры, мс (160); `gap` — пауза между цифрами, мс (100); `volume` — 0–63 (10). Цифры `0-9 * # A-D`. Для DTMF в SDP должен быть `telephone-event`: предложите его в `codecs` и убедитесь, что MM принял.

**Поля счётчиков**: `codec`, `local`, `remote`, `duration_sec`, `sent_packets`, `sent_bytes`, `received_packets`, `received_bytes`, `lost_packets`, `loss_percent`, `out_of_order_packets`, `duplicate_packets`, `jitter_ms`, `dtmf_sent`, `dtmf_received`, `dtmf_packets`, `other_payload_packets`, `other_payload_types`, `sources`, `bad_packets`. Смысл — в USAGE.md, раздел 8.

Что важно:
- Скорость отправки определяет `ptime` из SDP-**ответа** MM; `ptime` нашего offer определяет, как часто шлёт MM.
- Адрес назначения: параметр `host` → `c=` из SDP → адрес MM (если в ответе `0.0.0.0`, как у MM).
- `a=sendonly`/`a=inactive` в ответе: не отправляем, принимаем.
- Потоки, которые сценарий не остановил, останавливаются в конце сценария с предупреждением в логе.
- Незнакомый payload type в приходящем потоке считается в `other_payload_packets`, а не в `received_packets`.

## 8. Известные ограничения

- Нет `&&`/`||`/`else if`, арифметики, функций работы со строками (подстановка порта в SDP — через несколько готовых строк или через `rtp_open`, который сам формирует SDP).
- Нет подстановки переменных внутри `{...}`/`[...]` литералов.
- Неизвестные строки молча игнорируются.
- Видео и кодеки кроме перечисленных не поддерживаются. Воспроизведение готовых RTP-кадров из файла пока не реализовано.
