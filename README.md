# Тестер для media-manager

Тестер эмулирует SSW (управляющий сервер) для media-manager (MM): принимает от MM `Connect`, подключается к нему, выполняет сценарии (вызовы gRPC-методов MM), принимает события от MM и умеет слать и принимать настоящий RTP. Сценарии — простые текстовые файлы; команды берутся из `.proto` MM, поэтому новый метод MM сразу доступен в сценариях. Также есть нагрузочный режим и формат вывода, как при работе с `sipp`.

Устройство программы и то, как её расширять, описано отдельно: [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Быстрый старт

Инструкция для Linux (Ubuntu/Debian). Предполагается, что вы уже сделали `git clone`, а Go и остального нет. Перед началом нужны:

1. Папка с proto-файлами MM — репозиторий `ecss-media-manager-api-proto`. Нужен полный путь к ней.
2. IP тестера, до которого может достучаться MM (`hostname -I`).
3. Доступ к настройкам MM, чтобы указать адрес тестера.

### Установка и сборка

**Быстрый способ** — скрипт `setup.sh`: он проверит или поставит Go, спросит путь к proto и IP, запишет конфиг, соберёт тестер и прогонит его тесты:

```
bash setup.sh
```

**Вручную:**

1. Go версии 1.22 или новее (`go version`). Если его нет:

   ```
   wget https://go.dev/dl/go1.22.5.linux-amd64.tar.gz
   sudo rm -rf /usr/local/go
   sudo tar -C /usr/local -xzf go1.22.5.linux-amd64.tar.gz
   echo 'export PATH=$PATH:/usr/local/go/bin' >> ~/.bashrc
   source ~/.bashrc
   ```

2. Сборка (в первый раз скачивает библиотеки, 1-2 минуты; после каждого обновления кода пересобирайте):

   ```
   go build -o tester ./cmd/tester
   ```

3. Конфиг `config/config.json` — минимум три поля (остальное см. [Конфиг](#конфиг)):

   ```json
   {
     "proto_root": "/home/user/ecss-media-manager-api-proto",
     "proto_files": [
       "mm/client_api/v1/mm_client_api.proto",
       "mm/objects/v1/mm_objects.proto",
       "mm/server_api/v1/mm_server_api.proto"
     ],
     "local_server": { "address": "0.0.0.0", "port": 7000 },
     "rtp": { "ip": "10.30.100.108" }
   }
   ```

   `proto_root` — путь к proto; `rtp.ip` — ваш IP; порт `7000` обычно оставляют.

4. Проверка сборки (MM не нужен): `go test ./...` — везде `ok`.

5. В настройках MM укажите адрес и порт тестера (например, `10.30.100.108:7000`).

### Первый запуск и основные команды

Все запуски — одна команда `./tester` с разными сценариями и флагами, из корня репозитория:

| Что | Команда |
|---|---|
| Один сценарий (проверка, что всё работает) | `./tester -p config/config.json -s scripts/simple/channel_add.txt` |
| Один полный звонок с настоящим звуком | `./tester -p config/config.json -s scripts/many_steps/call_rtp.txt` |
| Все простые сценарии по очереди | `./tester -p config/config.json --continue-on-error -s scripts/simple` |
| Проверка кодеков и DTMF на MM | `./tester -p config/config.json -s scripts/mm_check` |
| Нагрузка: 20 звонков в секунду, 100 звонков за тест | `./tester -p config/config.json -s scripts/many_steps/call_rtp.txt --cps 20 --calls 100` |
| Работа в формате sipp | `./tester -p config/config.json -s scripts/many_steps/call_rtp.txt --calls 1000000 --cps 5 --screen` |

Тестер напишет «Сервер запущен… ожидаем подключения», дождётся, пока MM подключится к нему, и выполнит сценарий. Успех — «Сценарий завершился успешно» и `RC_SUCCESS` в ответах. Звук при этом не записывается; чтобы послушать, что присылает MM, запустите `scripts/simple/rtp_audio.txt` (он пишет WAV) или добавьте `record` в свой сценарий (см. [запись звука](#запись-звука)).

**Далее идет подробное описание различных аспектов работы с тестером.**

## Использование

### Как проходит запуск

1. Читается конфиг, загружаются proto-файлы (из них берутся методы, сообщения и enum — отдельного списка команд в тестере нет).
2. Разбираются **все** сценарии. Ошибка синтаксиса в любом из них останавливает тестер до начала работы.
3. Поднимается gRPC-сервер тестера (`local_server`), на котором MM вызывает `Connect`.
4. По `connect()` в сценарии (или автоматически перед сценарием) тестер дожидается `Connect` от MM, подключается к MM и аутентифицируется (`CredentialsSend`). Если MM отклонил аутентификацию, тестер останавливается с причиной (`reply_code`).
5. Выполняются сценарии, в конце печатается итог. Код возврата: `0` — всё успешно, `1` — были ошибки.

### Флаги

| Флаг | Описание |
|---|---|
| `-p`, `--path` | путь к конфигу (обязателен) |
| `-s`, `--scenario` | сценарии: файлы или папки. Можно списком через запятую, повторением флага или шаблоном shell (`-s scripts/simple/*`); всё, что идёт после `-s` в командной строке, считается сценариями |
| `--continue-on-error` | не останавливать сценарий на первой ошибке команды; в конце код возврата 1, если ошибки были |
| `--keep-alive` | не завершаться после сценария (чтобы MM мог продолжать присылать события) |
| `--cps`, `--parallel`, `--calls` | нагрузочный режим, см. [Нагрузочный тест](#нагрузочный-тест) |
| `--screen` | нагрузка с экраном, как в sipp, см. [Экран нагрузки](#экран-нагрузки---screen) |
| `--duration` | длительность `pause()` без аргумента в миллисекундах (как `-d` в sipp), см. [pause](#pause) |
| `--log-file ФАЙЛ` | дополнительно писать лог тестера в файл (перезаписывается при каждом запуске). Без флага файл не создаётся |
| `--verbose` | в нагрузочном режиме выводить подробный лог каждого клиента |

Откуда берутся сценарии (по убыванию приоритета): флаг `-s` → поле `scenarios` в конфиге → сценарий `scripts/many_steps/call_rtp.txt` (базовый звонок с RTP; путь относительно текущей папки, запускать из корня репозитория). Из папки берутся `*.txt` без вложенных папок, по алфавиту.

### Конфиг

```json
{
  "proto_root": "/path/to/ecss-media-manager-api-proto",
  "proto_files": [
    "mm/client_api/v1/mm_client_api.proto",
    "mm/objects/v1/mm_objects.proto",
    "mm/server_api/v1/mm_server_api.proto"
  ],
  "local_server": { "address": "0.0.0.0", "port": 7000 },

  "scenarios": ["scripts/simple", "scripts/many_steps/call.txt"],
  "start_delay_sec": 3,
  "load": { "cps": 20, "parallel": 100, "calls": 100 },
  "rtp": { "ip": "10.30.100.108", "port_min": 20000, "port_max": 30000 }
}
```

| Поле | Обязательно | Описание |
|---|---|---|
| `proto_root`, `proto_files` | да | где лежат proto MM; из них строятся все команды сценариев |
| `local_server.address/port` | да | где тестер слушает вызовы MM (`Connect` и события). MM должен быть настроен на этот адрес |
| `scenarios` | нет | сценарии по умолчанию, если нет `-s` |
| `start_delay_sec` | нет (3) | пауза после подключения к MM перед сценарием **без** своего `connect()`: MM нужно время, чтобы подключить свои серверы. `0` — без паузы |
| `load` | нет | значения `--cps/--parallel/--calls` по умолчанию; явно указанный флаг главнее |
| `rtp.ip` | нет (`127.0.0.1`) | адрес, который тестер пишет в SDP и на котором слушает RTP. **Должен быть доступен для MM** (не `127.0.0.1`, если MM на другой машине) |
| `rtp.port_min/port_max` | нет (20000–30000) | диапазон UDP-портов для RTP. Порты чётные, по одному на плечо звонка; выдача начинается со случайного порта, чтобы новый запуск не попадал на порты предыдущего (MM после `ChannelDestroy` может ещё слать RTP на старый порт) |

### Подключение к MM

Тестер играет роль SSW: сам он не подключается к MM, пока MM не вызовет на нём `Connect` (с адресом и портом MM и `session_id`). Дальше тестер подключается к MM и представляется ему через `CredentialsSend` (`instance = "tester"`).

- Соединение одно на весь запуск и общее для всех сценариев и клиентов нагрузки; повторные `Connect` игнорируются.
- Если MM не вызвал `Connect`, тестер ждёт: проверьте, что MM настроен на адрес и порт из `local_server`.
- В какой момент ждать — решает сценарий: см. [connect()](#connect).
- Логика подключения целиком в `internal/mmlink` (подробнее — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md)).

### Несколько сценариев

Сценарии идут по очереди (`-s scripts/simple`). Ошибка одного не мешает следующим (кроме случая, когда нет соединения с MM совсем: остальные помечаются пропущенными). У каждого сценария свои переменные. Все сценарии разбираются **до** запуска. В конце — итог и код возврата 1, если был сценарий с ошибкой:

```
Итог: сценариев 3, успешно 2, с ошибками 1
  OK       scripts/simple/channel_add.txt (0.4 с)
  ОШИБКА   scripts/simple/channel_audit.txt (0.2 с): сценарий остановлен на команде 2: ...
```

### Типовые задачи

Сами команды запуска — в таблице [выше](#первый-запуск-и-основные-команды). Здесь — что при этом происходит.

#### Один звонок с настоящим RTP

Сценарий `scripts/many_steps/call_rtp.txt` создаёт два плеча, шлёт тон (набор DTMF в сценарии сейчас закомментирован, п. 9), проверяет счётчики пакетов (`fail` при проблемах). Звук не записывается: чтобы включить запись, добавьте `record` в `rtp_start` (см. [запись звука](#запись-звука)).

#### Проверка кодеков и DTMF на реальном MM

По сценарию на кодек (PCMU, PCMA, G.722, L16/16000), на ptime 10/30 мс и на DTMF. Каждый сценарий сам проверяет результат командой `fail`, поэтому в итоговой таблице тестера он `OK` или `ОШИБКА` с причиной (`ПРОВАЛ ...`), а код возврата 0 только если всё прошло. Один сценарий: `-s scripts/mm_check/codec_g722.txt`. Если не проходит один кодек (у нас `L16`), проверьте, включён ли он на MM: без этого MM отвечает `RC_INTERNAL_ERROR` на `ChannelAdd`.

#### Нагрузочный тест

Один и тот же сценарий выполняют много клиентов. Каждый «звонок» — один полный прогон сценария одним клиентом; клиенты нумеруются с 1 (это переменная `INSTANCE`). Смысл флагов как у sipp (`-r`, `-l`, `-m`, `-d`), но названия явные, а сокращений нет.

Звонки стартуют **ровно по расписанию**: с шагом `1/cps` секунды, без пачек и без «догоняния». Нагрузка получается ровной, а не волнами.

| Флаг | Что задаёт | По умолчанию |
|---|---|---|
| `--cps N` | **cps (calls per second)**: сколько новых звонков начинать в секунду (можно дробное: `0.5` — один звонок в 2 с) | 10 |
| `--parallel N` | сколько звонков может идти **одновременно** (потолок) | без ограничения |
| `--calls M` | сколько всего звонков сделать; `0` — до Ctrl+C | без ограничения |
| `--duration MS` | длительность `pause()` без аргумента | `pause()` пропускается |

Нагрузочный режим включается, если указан хотя бы один из `--cps`, `--parallel`, `--calls` (или они заданы в секции `load` конфига).

Сколько звонков идёт одновременно, получается само: `cps × длительность звонка`. Если оно упёрлось в `--parallel`, очередной старт ждёт, пока какой-то звонок завершится; пропущенные старты потом не нагоняются (расписание сдвигается), поэтому после упора нет всплеска.

Примеры (звонок из `call_rtp.txt` идёт около 5 с: `hold_seconds = 5`):

| Запуск | Что происходит |
|---|---|
| `--cps 1 --calls 100` | один новый звонок в секунду, всего 100 |
| `--cps 20 --calls 100` | по 20 стартов в секунду, набор за 5 с, около 100 одновременных |
| `--cps 5` | 5 звонков в секунду без конца, около 25 одновременных; остановка по Ctrl+C |
| `--cps 10 --parallel 30 --calls 1000` | 10 стартов/с дали бы ~50 одновременных, но потолок 30: реальный темп снизится до ~6 звонков/с (30 / 5 с) |
| `--cps 1 --parallel 100000 --calls 10000000 --duration 5000` | то же, что у sipp `-r 1 -l 100000 -m 10000000 -d 5000`: 1 звонок в секунду, `pause()` в сценарии по 5 с |

Ctrl+C: первое нажатие прекращает запуск новых звонков, тестер дожидается идущих и печатает сводку; второе — выход сразу.

Остальное про нагрузочный режим:
- У каждого клиента свои переменные, RTP-порты и RTP-сеансы; общие только соединение с MM, поток событий и выдача портов. Строки лога клиента начинаются с `[#N]`, подробный лог отключён (остаются `log(...)` и ошибки; `--verbose` включает всё).
- Ход печатается раз в 5 секунд. В конце — сводка: звонков успешно/с ошибкой и процент успеха; длительность звонков (мин / средняя / 95-й процентиль / макс); RTP по всем потокам (отправлено / принято / потеряно, средний и максимальный джиттер); потоки без входящего звука, потоки с несколькими SSRC, DTMF, чужие payload type; ошибки, сгруппированные по тексту, с числом клиентов. Код возврата 1, если хоть один клиент провален.
- Диапазон портов должен вмещать все одновременные звонки (по два порта на звонок): для 100 одновременных звонков нужно 200 портов, по умолчанию их 5000.
- Чтобы не плодить сотни WAV-файлов, пишите звук только у части клиентов: `if INSTANCE == 1 { rtp_start(..., record = "...") } else { rtp_start(...) }`. В одиночном запуске `INSTANCE` равен 1.
- События от MM общие для всех клиентов, поэтому в `wait_event` обязательно фильтруйте по идентификаторам своего канала.

### Экран нагрузки (--screen)

Нагрузка в духе sipp: тестер рисует в терминале экран, а частоту звонков и паузу меняешь клавишами прямо во время теста.

```
./tester -p config/config.json -s scripts/many_steps/call_rtp.txt --screen --calls 1000
```

Из флагов достаточно `--calls` (можно и без него: тест идёт до `q`). `--cps` и `--parallel` задают начальные значения; без `--cps` стартовая частота 10 звонков в секунду.

Надписи на экране как у sipp. Сверху общая статистика: состояние, время, `cps` (заданное и фактическое за последние 5 с), сколько звонков запущено, идёт сейчас, завершено и с ошибкой, длительность звонков (min / avg / max), последняя ошибка.

Блок **RTP** показывает трафик по всем RTP-потокам тестера и отвечает на вопрос «шлёт ли MM звук на тестер»:
- `RTP streams` — сколько потоков идёт сейчас и сколько из них **без входящих пакетов** (дольше 2 с от запуска потока не пришло ни одной датаграммы). Если таких больше нуля, рядом появляется пометка `<-- MM sends nothing to these`: либо MM не шлёт RTP на порт тестера, либо шлёт на другой адрес или порт (проверьте `rtp.ip` и SDP). В скобках — завершённые потоки и сколько из них не получили ничего.
- `RTP in` — все датаграммы, дошедшие до портов тестера, и скорость в пакетах в секунду. Из них `audio` — звук нужного кодека, `dtmf` — события telephone-event, `other` — неизвестный payload type, `bad` — не RTP. Дальше потерянные по нумерации пакеты и наибольший джиттер.
- `RTP out` — сколько отправил тестер и с какой скоростью.

Числа накапливаются с запуска тестера (по всем сценариям) и включают завершённые потоки, поэтому не убывают. Подробная статистика по каждому потоку, как раньше, доступна в сценарии через `rtp_stop` и в итоговой сводке.

Ниже таблица действий сценария в порядке записи: запросы к MM (имя метода из proto), `wait_event`, `connect()`, `sleep`, `pause`, `rtp_*`. Колонки: `Running` — сколько клиентов выполняют команду сейчас, `Done` — сколько раз выполнена, `Failed` — сколько раз с ошибкой. Присваивания, `log`, `fail`, `for` и `if` в таблицу не попадают; команды внутри блоков показываются. Номер у строки тот же, что в [логе](#лог) (`2.1` внутри `for` и ветки `then`, `3.else.1` в ветке `else`), поэтому по нему легко найти команду в сценарии. Пропуски в нумерации — это скрытые строки.

| Клавиша | Действие |
|---|---|
| `+`, `-` | cps плюс или минус 1 (минимум 0.1) |
| `*`, `/` | cps плюс или минус 10 |
| `p` | пауза: новые звонки не запускаются, идущие доигрываются; повторное `p` продолжает без «догоняния» |
| `q` | завершить: новые звонки не запускаются, тестер ждёт идущих и печатает сводку |
| `Q` | выйти сразу |

Ctrl+C работает как `q`; второй раз — выход сразу.

Что важно знать:
- Лог тестера на экран не выводится, чтобы не портить таблицу, и по умолчанию нигде не сохраняется (файлы не создаются). Чтобы сохранить лог, добавьте `--log-file tester.log`. Итоговая сводка печатается в терминал после выхода с экрана.
- Нужен настоящий терминал (не вывод в файл и не `ssh` без tty): клавиши читаются без Enter через команду `stty` (Linux, macOS).
- Если сценариев несколько, они идут по очереди, у каждого свой экран; после `q` следующие не запускаются.

### Лог

```
2026/10/08 12:00:01 [1] Команда: ChannelAdd
2026/10/08 12:00:01 Запрос для ChannelAdd: {...}
2026/10/08 12:00:01 Ответ для ChannelAdd: {...}
```

- `[N]` — номер команды в сценарии; внутри `for` и ветки `then` — `2.1`, `2.2` (номер блока.номер команды), в ветке `else` — `2.else.1`.
- Запросы, ответы и события печатаются с именами полей **как в proto** (`channel_id`) — под этими же именами они доступны в сценарии.
- «Получен запрос: …» — событие от MM (оно попадает в буфер для `wait_event`).
- `log: …` — вывод команды `log(...)`.
- Итог RTP при `rtp_stop`: кодек, отправлено/принято/потеряно, джиттер и т. п.

### Счётчики RTP

Их возвращают `rtp_stats` и `rtp_stop` (поля читаются как `st.received_packets`).

| Поле | Смысл |
|---|---|
| `codec`, `local`, `remote`, `duration_sec` | выбранный кодек, локальный и удалённый адрес, длительность |
| `sent_packets`, `sent_bytes` | отправлено нами |
| `received_packets`, `received_bytes` | принято от MM (только согласованный audio payload) |
| `lost_packets`, `loss_percent` | потери по разрывам в sequence number (RFC 3550) |
| `out_of_order_packets`, `duplicate_packets` | переупорядочение и дубли |
| `jitter_ms` | межпакетный джиттер по RFC 3550 |
| `dtmf_sent`, `dtmf_received`, `dtmf_packets` | цифры и пакеты telephone-event |
| `other_payload_packets`, `other_payload_types` | пакеты с чужим payload type (например, MM шлёт 101, а договорились о 96) |
| `sources` | сколько разных SSRC принято. Больше 1 — в поток подмешан чужой источник (например, остатки предыдущего звонка на том же порту) |
| `bad_packets` | не RTP |

Если `received_packets` примерно вдвое больше ожидаемого, а `jitter_ms` около 0 — смотрите `sources`: скорее всего, два потока на один порт.

### Диагностика

| Симптом | Что проверить |
|---|---|
| `Proto path: proto` / не находит proto | запущен старый бинарник: пересоберите (`go build -o tester ./cmd/tester`) и проверьте `proto_root` в конфиге |
| Тестер долго пишет «ожидаем подключения» | MM не вызвал `Connect`: адрес и порт `local_server` в настройках MM, доступность порта |
| `MM отклонил подключение: reply_code=...` | MM не принял `CredentialsSend`; причину смотрите в логе MM |
| `нет соединения с MM` при вызове метода | в сценарии `connect()` стоит ниже первого вызова метода — переместите его в начало |
| `метод X не найден` | опечатка или proto не той версии; список методов берётся из `proto_files` |
| `поле 'x' не найдено (есть: ...)` | имя поля не как в proto (`channelId` вместо `channel_id`); в ошибке перечислены доступные поля |
| Сценарий остановился на `reply_code ... не RC_SUCCESS` | это ожидаемое поведение; с `--continue-on-error` можно проверять статус в `if` |
| `ChannelAdd` → `RC_INTERNAL_ERROR` на конкретном кодеке | кодек не включён на MM (так у `L16`) |
| `received_packets = 0` | MM шлёт на другой адрес: проверьте `rtp.ip` (виден ли он MM), `c=` в SDP-ответе, firewall |
| Принято вдвое больше пакетов, `sources` > 1 | на порт приходит ещё и поток от прошлого запуска: запустите ещё раз с паузой или сдвиньте диапазон портов |
| `wait_event` по таймауту | в ошибке показаны пришедшие события с тем же именем, но не подошедшие под условия — сравните поле и значение |
| Команда «молча» ничего не делает | парсер игнорирует нераспознанные строки (известная слабость); проверьте синтаксис по разделу [Работа со сценариями](#работа-со-сценариями) |
| `Ошибка запуска сервера … address already in use` | порт `local_server` занят (возможно, тестер уже запущен) |

## Работа со сценариями

Сценарий — текстовый файл (по соглашению `.txt`), команды выполняются сверху вниз. Все примеры ниже есть в `scripts/`.

### Общие правила

- Одна команда — одна строка. Исключение — блоки `for` и `if` (`{ ... }`).
- Комментарии: строка, начинающаяся с `#` или `//`. Пустые строки игнорируются.
- **Опасность:** строка, которую парсер не распознал как команду, пропускается без ошибки. Опечатка в `sleep`/`log` может остаться незамеченной — проверяйте вывод сценария на первом запуске.
- Все сценарии разбираются до запуска; неизвестный метод MM, неверное число аргументов `rtp_*`, незакрытая скобка — ошибка при разборе с номером строки.

### Значения и переменные

Любой аргумент и правая часть присваивания — «значение». Значения вычисляются в таком порядке:

| Запись | Что это |
|---|---|
| `"текст"` | строка; внутри работают `\r`, `\n`, `\t`; запятая и скобки внутри кавычек безопасны |
| `123`, `0.5`, `-4` | число |
| `true`, `false`, `null` | булево / null |
| `[ ... ]`, `{ ... }` | JSON-массив/объект «как есть» (см. [ниже](#объекты-и-массивы-в-аргументах)) |
| `var.field.sub` | поле объекта в переменной (JSON); числа остаются точными, в том числе 64-битные ID |
| `ИМЯ_ENUM` | значение enum по имени из proto, например `RC_SUCCESS`, `ACT_MODIFY` |
| `var` | значение переменной |
| `SESSION_ID`, `INSTANCE` | встроенные переменные (см. ниже) |

Неизвестное имя — ошибка «непонятное rvalue значение».

#### Присваивание и имена полей

```
sdp = "v=0\r\n..."          # строка
n = 5
chan = ChannelAdd(...)       # результат вызова метода MM → JSON ответа (с нулевыми полями)
```

Переменные — строки; объекты хранятся как JSON. Из ответа читаем `chan.channel_id`, `chan.reply_code`. Имена полей **везде такие же, как в proto** (`channel_id`, `reply_code`): в переменных, в логе запросов и ответов, в условиях `wait_event`, в статистике RTP. Запись `chan.channelId` не работает; при опечатке ошибка перечисляет доступные поля.

#### Запись в поле объекта

```
port_info = {"action": "ACT_MODIFY", "sdp_answer": "", "sdp_offer": ""}
port_info.sdp_answer = rtp_b.sdp        # переменная.поле = значение
port_info.inner.x = 5                   # вложенные поля
```

Справа — значение (строка, число, переменная, `var.поле`); результат команды в поле записать нельзя. Переменная должна существовать и быть объектом.

#### Встроенные переменные

- `SESSION_ID` — идентификатор сессии, полученный от MM в `Connect`. Определена после `connect()`.
- `INSTANCE` — номер клиента в нагрузочном режиме (с 1; в обычном запуске всегда 1).

#### Объекты и массивы в аргументах

```
audio_info = [{"type": 2, "url_file": "http://example.com/file.wav", "duration": 10}]
dtmf = {"type": 1, "pass_through_mode": false}
```

- Внутри `{...}` и `[...]` **подстановки переменных нет**: это JSON, который передаётся как есть (имена полей — ровно как в proto, например `on_ms`; неизвестное поле — ошибка). Чтобы вставить переменную, соберите объект по частям: `obj = {...}`, потом `obj.field = var`.
- Имена enum внутри JSON пишутся строкой: `"action": "ACT_MODIFY"`.
- Вложенные `oneof` задаются именем поля: `{"tone_info": {...}}` (см. `channel_audio_sequence_play.txt`).

### Вызов метода MM

```
resp = ChannelAdd(SESSION_ID, 0, 0, true, sdp_offer, 0, "")
ChannelDestroy(SESSION_ID, resp.channel_id)
```

- Имя метода — как в proto (`ChannelAdd`, `ChannelDestroy`, `ChannelAudioFilePlay`, …). Любой rpc из загруженных proto доступен без изменений тестера.
- Аргументы идут **по порядку полей запроса в proto** (по номеру в объявлении сообщения). Для `ChannelAddRequest`: `session_id, context_id, channel_id, need_media, sdp_offer, media_profile_id, site`. Недостающие хвостовые аргументы остаются значениями по умолчанию; лишние — отбрасываются.
- `resp = ...` необязательно. Без него ответ только логируется.
- Если в ответе есть `reply_code` и он не `RC_SUCCESS` — команда считается ошибкой, сценарий останавливается (но ответ всё равно сохраняется в переменную). С `--continue-on-error` сценарий идёт дальше, код возврата в конце — 1.
- Таймаут вызова — 5 секунд.
- Вызов метода до `connect()` (если он есть в сценарии) — ошибка «нет соединения с MM».

### Управление потоком выполнения

#### for

```
for i in 1..100 {
    resp = ChannelAdd(SESSION_ID, 0, 0, true, sdp_offer, 0, "")
    resp = ChannelDestroy(SESSION_ID, resp.channel_id)
}
```

Границы включительно: число или переменная (`1..n`). Если `a > b`, тело не выполняется. Переменная цикла доступна в теле и после цикла. Циклы вкладываются.

#### if / else

```
if resp.reply_code == RC_SUCCESS {
    ...
} else {
    log("не удалось:", resp.reply_code)
}
```

- Одно сравнение: `==  !=  <  >  <=  >=`. Нет `&&`, `||`, `else if` (вкладывайте `if`).
- Оба значения числа → числовое точное сравнение (большие ID не теряют точность, `2 < 10`). Иначе `==`/`!=` сравнивают строки, а `<`, `>` и т. п. дают ошибку.
- Имя enum приводится к числу, `resp.reply_code == RC_SUCCESS` работает.
- Чтобы проверять `reply_code` в `if`, запускайте с `--continue-on-error` (иначе сценарий остановится раньше).

#### Стиль скобок

`{` можно писать в конце строки или на следующей; `else` — после `}` или с новой строки; между ними допустимы пустые строки и комментарии. `}` — всегда на отдельной строке (или `} else {`).

#### sleep

`sleep(2)`, `sleep(0.5)`, `sleep(delay)` — пауза в секундах.

#### pause

`pause()` — пауза, длительность которой задаётся флагом `-d` в миллисекундах (как `<pause/>` и `-d` в sipp): одним сценарием можно проверять звонки разной длины, не правя файл. Без `-d` пауза пропускается. `pause(5000)` — явная длительность в миллисекундах, флаг `-d` на неё не влияет.

#### log и fail

```
log("канал:", resp.channel_id, "код:", resp.reply_code)
fail("мало пакетов:", st.received_packets)
```

- `log` печатает аргументы одной строкой через пробел (`log: ...`).
- `fail` печатает так же и завершает команду **ошибкой**: сценарий останавливается (с `--continue-on-error` идёт дальше, но завершится с кодом 1). В нагрузочном режиме клиент считается проваленным, текст попадает в сводку ошибок.
- Типичная проверка: `if st.received_packets < 20 { fail("мало пакетов:", st.received_packets) }`.

#### connect()

```
connect()
sleep(3)
resp = ChannelAdd(SESSION_ID, ...)
```

Ждёт `Connect` от MM, подключается и аутентифицируется. Если соединение уже есть — пропускается, поэтому безопасно ставить в начало каждого сценария. Без `connect()` в сценарии тестер подключается сам перед запуском и ждёт `start_delay_sec` из конфига. С `connect()` пауза после него — обычный `sleep`. До `connect()` переменная `SESSION_ID` не определена.

### Ожидание событий: wait_event

MM не только отвечает на запросы, но и вызывает методы на тестере (события: `AudioFilePlayed`, `AudioSequencePlayed`, `DTMFDetected`, `RtpIncoming` и др.). Чтобы не гадать `sleep`'ом:

```
play = ChannelAudioFilePlay(SESSION_ID, chan.channel_id, audio_info)
ev = wait_event(AudioFilePlayed, channel_id == chan.channel_id, player_id == play.player_id, 15)
log("проиграно, player_id:", ev.player_id)
```

- Синтаксис: `[переменная =] wait_event(ИмяСобытия, условие, ..., секунды)`. Имя — метод proto, который MM вызывает на тестере (можно в кавычках); опечатка ловится при разборе.
- Условие: `поле оператор значение`; слева поле события (имя как в proto и в логе, вложенные через точку), справа любое значение сценария. Операторы — как в `if`. Должны выполниться все условия.
- Последний аргумент без оператора — таймаут в секундах (число/переменная, дробный, `0` — только проверить уже пришедшие). По умолчанию 10 с.
- Событие, пришедшее **до** `wait_event`, не теряется (события копятся с начала сценария). События предыдущих сценариев не учитываются.
- Каждое событие забирается один раз: два `wait_event` подряд получат два разных события, по порядку прихода.
- По таймауту ошибка показывает, что пришло на самом деле (события с таким именем, не подошедшие под условия, и счётчики остальных), так видны опечатки в поле или значении.
- В нагрузочном режиме обязательно фильтруйте по своим идентификаторам (`channel_id == ...`): события общие для всех клиентов.

### RTP-команды

Тестер может слать и принимать настоящий RTP на порты из SDP. Кодеки: PCMU, PCMA, G.722, L16 (8–48 кГц), DTMF — telephone-event (RFC 4733). Звук — синусоида заданной частоты.

```
rtp  = rtp_open()                                # занять порт; rtp.sdp — готовый SDP-offer
chan = ChannelAdd(SESSION_ID, 0, 0, true, rtp.sdp, 0, "")
rtp_start(rtp, chan.sdp_answer, tone = 440, record = "in_{id}.wav")
sleep(5)
st = rtp_stop(rtp)
log("принято:", st.received_packets, "потеряно:", st.lost_packets)
```

| Команда | Что делает |
|---|---|
| `r = rtp_open(...)` | занимает UDP-порт, в `r`: `id`, `ip`, `port`, `sdp` (offer) |
| `rtp_start(r, sdp_ответа, ...)` | берёт из ответа MM адрес, порт, кодек и `ptime`, запускает отправку и приём |
| `rtp_dtmf(r, "123#", ...)` | шлёт цифры в том же потоке, возвращается, когда переданы |
| `st = rtp_stats(r)` | текущие счётчики (поля — в разделе [Счётчики RTP](#счётчики-rtp)) |
| `st = rtp_stop(r)` | останавливает поток, освобождает порт, итоговые счётчики |

**rtp_open** (все параметры необязательны, именованные `имя = значение`):

| Параметр | Описание |
|---|---|
| `ip` | адрес в SDP и для сокета |
| `port` | конкретный порт вместо свободного |
| `codecs` | `"PCMA"`, `"PCMA,PCMU"`, `"G722"`, `"L16/16000"`, `"PCMA,telephone-event"`; порядок = предпочтение; по умолчанию `PCMU,PCMA` |
| `dtmf_pt` | payload type telephone-event, 96–127 (по умолчанию 101) |
| `ptime` | мс (по умолчанию 20) |

Вместо параметров можно передать готовый SDP: `rtp_open(sdp_offer)` — берутся адрес и порт из него.

**rtp_start**: `tone` — частота, Гц, целое (440; `0` — тишина); `file` — WAV-файл, который играется вместо тона (см. [файл вместо тона](#файл-вместо-тона)); `tone` и `file` вместе не задаются; `record` — файл для записи принятого звука (см. [запись звука](#запись-звука)); `send = false` — только принимать; `host` — слать на этот адрес вместо адреса из SDP.

**rtp_dtmf**: `duration` — длительность цифры, мс (160); `gap` — пауза между цифрами, мс (100); `volume` — 0–63 (10). Цифры `0-9 * # A-D`. Для DTMF в SDP должен быть `telephone-event`: предложите его в `codecs` и убедитесь, что MM принял.

Что важно:
- Скорость отправки определяет `ptime` из SDP-**ответа** MM; `ptime` нашего offer определяет, как часто шлёт MM.
- Адрес назначения: параметр `host` → `c=` из SDP → адрес MM (если в ответе `0.0.0.0`, как у MM).
- `a=sendonly`/`a=inactive` в ответе: не отправляем, принимаем.
- Потоки, которые сценарий не остановил, останавливаются в конце сценария с предупреждением в логе.
- Незнакомый payload type в приходящем потоке считается в `other_payload_packets`, а не в `received_packets`.

#### Файл вместо тона

Параметр `file` у `rtp_start` заставляет слать в MM звук из WAV-файла вместо синуса. Так можно проверить, что звук проходит через MM целиком (речь, свой тестовый сигнал), а не только то, что пакеты идут.

```
rtp_start(rtp_a, answer_1, file = "speech.wav", record = "call_A_{id}.wav")
```

- Формат: WAV, PCM 16 бит, любая частота, моно или стерео (стерео сводится к моно). Другие форматы тестер отклонит с подсказкой; конвертация: `ffmpeg -i in.mp3 -ar 8000 -ac 1 -c:a pcm_s16le speech.wav`.
- Файл проигрывается по кругу, пока не вызван `rtp_stop`; последний неполный пакет добивается тишиной. Звук приводится к частоте выбранного кодека (линейной интерполяцией) и кодируется один раз на сочетание «файл + кодек + ptime», поэтому нагрузка от числа потоков почти не растёт.
- Путь — относительно папки запуска. Если файла нет или он не подходит, `rtp_start` вернёт ошибку. Файл читается целиком (не больше 64 МБ).
- Файл целиком хранится в памяти в закодированном виде — не берите часовые записи.
- Пример: `scripts/simple/rtp_file.txt`.

#### Запись звука

Параметр `record` у `rtp_start` включает запись; без него ничего не пишется.

```
rtp_start(rtp_a, answer_1, tone = 440, record = "call_A_{id}.wav")
```

- Пишется только **входящий** звук (то, что прислал MM), не отправляемый тестером.
- Формат: WAV, 16 бит, моно, PCM; частота кодека — 8 кГц, у G.722 и L16/16000 — 16 кГц. Это звук, а не сетевой дамп: заголовков RTP и таймингов в файле нет (не pcap).
- Пакеты с цифрами DTMF в файл не попадают, на их месте тишина.
- Имя файла — любой путь относительно папки запуска; `{id}` заменяется номером RTP-сеанса (не клиента нагрузки). Файл создаётся в момент `rtp_start`, существующий перезаписывается. Папку тестер не создаёт: если её нет, `rtp_start` вернёт ошибку.
- На месте потерянных пакетов вставляется тишина (не более секунды за раз), чтобы длительность и ритм не съезжали; запоздавшие пакеты отбрасываются. Если на порт идёт несколько потоков (`sources` > 1), они пишутся в один файл вперемешку.
- Файл закрывается при `rtp_stop` (или в конце сценария); ошибка записи вернётся из `rtp_stop`.
- WAV-файлы в git не попадают (`*.wav` в `.gitignore`).

### Ограничения языка

- Нет `&&`/`||`/`else if`, арифметики, функций работы со строками (подстановка порта в SDP — через `rtp_open`, который сам формирует SDP).
- Нет подстановки переменных внутри `{...}`/`[...]` литералов.
- Неизвестные строки молча игнорируются.
- Видео и кодеки кроме перечисленных не поддерживаются. Воспроизведение готовых RTP-кадров из файла пока не реализовано.

## Разработка

```
go test ./...                  # все тесты (MM не нужен: сеть заменяется локальными UDP-сокетами и заглушками)
go test -race ./internal/...   # с проверкой гонок
```

Устройство программы, потоки данных, как добавить команду, кодек или поле статистики — в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md). После каждого изменения кода пересобирайте бинарник (`go build -o tester ./cmd/tester`).
